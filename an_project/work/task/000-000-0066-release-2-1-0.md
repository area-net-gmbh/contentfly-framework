# Release v2.1.0 — die Sicherheitskorrekturen ausliefern

## Context
**Die Korrekturen vom 2026-09-18 liegen auf `master`, aber nicht im Paket.** Wer Contentfly per
Composer bezieht, hat `v2.0.0` — mit SQL-Injection (`0062`), DQL-Injection (`0063`), Tree-Routen
ohne Rechteprüfung (`0061`) und ungeprüftem Überschreiben von Dateien (`0060`). Die Lücken sind im
öffentlichen Repository beschrieben. Dazu kommen die i18n-Korrekturen (`0059`, `0064`) und die
MIT-Lizenz (`0065`).

**Entschieden vom Auftraggeber am 2026-09-18: `v2.1.0`**, nicht `v2.0.1`. Zwei Änderungen spürt
ein Client — 403 bei den Tree-Routen ohne Leserecht, 400 statt 500 bei unbekannten Feldnamen —,
und dazu kommt eine neue Funktion (Übersetzungen lassen sich wieder anlegen).

## Acceptance criteria
- [x] Die Version ist an allen Stellen `2.1.0`: `version.php`, `options.versions` in `composer.json`, `apidoc.json`, der Lock-Eintrag.
- [x] Das Register (`breaking-changes.md`) führt jede Änderung, die ein Projekt merkt, mit „ausgeliefert mit `v2.1.0`".
- [x] Der Leitfaden (`migration.md`) hat einen Weg „Von 2.0 auf 2.1" für Projekte, die schon auf 2.0 laufen, und nennt die neuen Zahlen des Registers.
- [x] Der Tag `v2.1.0` ist gesetzt, der Veröffentlichungslauf grün, und das Paket-Repository trägt ihn.
- [x] Ein frisches Projekt mit `^2.0` bezieht `v2.1.0` — gemessen, nicht angenommen.

## Verification
Wie bei `v2.0.0` (`011-004-0003`): frisches Verzeichnis, `"areanet/contentfly": "^2.0"`,
`composer update` → `version: v2.1.0` aus dem Paket-Repository. Dazu das Bezugsweg-Gate im
nächsten Lauf.

## Reihenfolge
Wie bei `v2.0.0` erzwungen: **erst Merge, dann Tag.** Das Bezugsweg-Gate läuft im Pull Request
gegen das veröffentlichte Paket; der Tag entsteht auf dem gemergten `master`.

## Stand nach dem ersten Schritt
**Versionsnummern, Register und Leitfaden sind vorbereitet.**

- **Register:** fünf neue Einträge unter *API* — Tree-Routen, Löschprotokoll, Feldnamen,
  Überschreiben von Dateien, Übersetzungen. Jetzt 124 Einträge in 14 Abschnitten.
- **Leitfaden:** neuer Abschnitt *Von 2.0 auf 2.1* mit vier Schritten; der entscheidende ist das
  **Prüfen der Rechte**, weil ein Baum ohne `Permission`-Zeile jetzt 403 liefert statt still Daten.
  Die Zahl der API-Einträge in Phase 8 stand schon vor dieser Änderung falsch (24 statt 28) und
  ist jetzt 33.
- **`pentest-spec.md`** nennt `v2.1.0` als Bezugsversion — gegen `v2.0.0` zu prüfen hiesse,
  behobene Lücken nachzuweisen.
- **Der Lock war veraltet — auch auf `master`, auch für den aktuellen Composer (2.10.3).** Er
  kopiert das Manifest aus `lib/contentfly/` in den Eintrag von `areanet/contentfly`; jede Änderung
  daran, zuletzt die MIT-Lizenz, liess ihn veralten. Aktualisiert mit
  `composer update areanet/contentfly --no-install`; **nur dieser eine Eintrag** hat sich
  geändert (Version, Lizenz, Manifest-Kopie, Referenz) — gegen `HEAD` verglichen.


## Ergebnis — `v2.1.0` steht (2026-09-18)
**Tag `v2.1.0`** auf dem Merge-Commit von #27 (`84f7e658`), annotiert wie `v2.0.0`, mit den
geschlossenen Lücken und dem Verweis auf *Von 2.0 auf 2.1*. Der Workflow *Paket veröffentlichen*
lief grün; das Paket-Repository trägt `v2.1.0` auf `85d070e1`, neben `v2.0.0`.

**Abnahme gemessen**, wie bei `v2.0.0`: frisches Verzeichnis, `"areanet/contentfly": "^2.0"`,
`composer update` mit Composer 2.10.3:

```
versions : * v2.1.0
license  : MIT License (MIT) (OSI approved)
source   : [git] git@github.com:area-net-gmbh/contentfly-framework-dist.git 85d070e1cb44…
51 Pakete · APP_VERSION 2.1.0 · LICENSE liegt im Paket · composer audit: keine Advisories
```

**Die Abnahme ist zweimal gescheitert, bevor sie gelang — beide Male an der Maschine, nicht am
Paket**, und beides lehrreich für jeden, der sie wiederholt:

1. **Ein veralteter Composer-Cache.** Composer konnte seinen Git-Spiegel nicht aktualisieren
   (`Could not fetch origin`) und bot deshalb nur `v2.0.0` an — **ohne Fehler**, die Auflösung
   sah einfach aus wie „2.0.0 ist die neueste". Wer die Abnahme nur auf „läuft durch" prüft, nimmt
   das falsche Release ab. Gegenmittel: eigener, leerer `COMPOSER_CACHE_DIR`.
2. **Der richtige Schlüssel.** Dieses Repository setzt in `.git/config` ein eigenes
   `core.sshCommand` (`~/.ssh/id_ed25519_areanet`). Ausserhalb des Repos — also in einem frischen
   Projektverzeichnis — gilt das nicht; dazu schrieb eine globale Composer-Konfiguration die
   SSH-Adresse auf HTTPS mit einem Token um, das beim Paket-Repository scheitert. Gegenmittel:
   eigenes `COMPOSER_HOME` und `GIT_SSH_COMMAND` mit dem Schlüssel.
