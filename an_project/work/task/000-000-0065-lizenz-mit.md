# Contentfly 2 unter MIT stellen — Lizenzangaben vereinheitlichen

## Context
**Gefunden bei der Planung von `000-000-0056` am 2026-09-18.** Das Repository ist öffentlich, und
seine Lizenzangaben widersprachen sich:

| Stelle | Stand |
|---|---|
| `LICENSE` | „CONTENTFLY CMS is licensed under a dual license … open-source-version, licensed under MIT", Copyright 2019 |
| `composer.json` (Wurzel und Paket) | `"license": "proprietary"` |
| `README.md` / Paket-README | „Proprietär" / „Proprietary" |
| `lib/contentfly/` (Inhalt des veröffentlichten Pakets) | **keine** `LICENSE` |

Für ein öffentliches Repository ist das mehr als Kosmetik: Wer den Code einsetzen will, kann
nicht sagen, unter welchen Bedingungen. Und der kostenlose OSS-Plan von SonarQube Cloud setzt ein
öffentliches Projekt **mit Open-Source-Lizenz** voraus.

**Entschieden vom Auftraggeber am 2026-09-18: MIT, Open Source.**

## Acceptance criteria
- [ ] `LICENSE` ist der reine MIT-Text — ohne den Dual-License-Vorspann, Copyright 2019–2026 AREA-NET GmbH.
- [ ] `lib/contentfly/LICENSE` existiert: Das Paket entsteht per Subtree-Split nur aus `lib/contentfly/`, und MIT verlangt, dass der Lizenztext jede Kopie begleitet.
- [ ] `composer.json` in Wurzel und Paket sagen `"license": "MIT"`.
- [ ] Beide READMEs nennen MIT.

## Verification
`composer validate` für beide Manifeste; `grep` findet im Framework keine `proprietary`-Angabe mehr.

## Ergebnis
Alle vier Punkte umgesetzt.

**Bewusst unverändert:** `tools/ci/bezugsweg-pruefen.sh` legt ein **Kundenprojekt** zur Probe an
und gibt ihm `"license": "proprietary"`. Das ist richtig: Ein Projekt, das ein MIT-Framework
einsetzt, darf selbst proprietär sein.

**Das frühere Contentfly CMS 1.x ist nicht betroffen** — ein eigenes Produkt mit eigener
Codebase (siehe `SECURITY.md`). Das README sagt das jetzt ausdrücklich, weil der alte
`LICENSE`-Vorspann vom „CONTENTFLY CMS" sprach.

**Wirksam wird die neue Lizenz für das Paket mit dem nächsten Tag**, weil erst dann der Split
den Stand nach `contentfly-framework-dist` bringt. `v2.0.0` bleibt, wie es veröffentlicht wurde.

**Nebenbefund, nicht behoben:** `composer validate` meldet den Lock als veraltet gegenüber
`composer.json` — **schon auf `master` vor dieser Änderung**, geprüft durch Zurücksetzen der
Lizenzzeile. Die Lizenz fliesst in den Content-Hash nicht ein. Ursache ungeklärt; eigenes Ticket
wert.
