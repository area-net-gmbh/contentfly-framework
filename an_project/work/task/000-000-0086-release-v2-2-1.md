# Release v2.2.1 — den Host-Block-Fix ausliefern

## Context
**Seit `v2.2.0` liegt ein Pull Request auf `master` (#48), aber nicht im Paket:** `000-000-0085` —
der Host-Block wird jetzt gewählt, bevor `display_errors` und `is_installed` die Konfiguration
lesen. Bis dahin lasen beide den Default-Block, und ein Server mit `APP_DEBUG = false` im
Host-Block lieferte trotzdem Fehlerausgabe in der Antwort, samt absoluter Serverpfade. Gefunden auf
dem UFP-Staging mit `v2.2.0`; UFP wartet auf die Auslieferung.

**`v2.2.1`, nicht `v2.3.0`** — anderer Massstab als bei `0084`. Dort spürte ein Projekt neun
Registereinträge, darunter zwei Entfernungen und eine neue Einstellung; das war ein Minor. Hier ist
es ein Fix mit **einem** Registereintrag, ohne Entfernung und ohne neuen Schlüssel. Wer keine
Host-Blöcke benutzt, merkt nichts.

**Offenes Ende daneben, kein Teil dieses Tasks:** Die Abschluss-Buchführung zu `000-000-0084` liegt
als Commit `6f24d646` ungepusht auf `chore/000-000-0084-abschluss`. Auf `master` steht `0084`
deshalb noch auf `in-progress` mit zwei offenen Haken, obwohl `v2.2.0` getaggt (`799d38a0`),
veröffentlicht und abgenommen ist. Das gehört in einen eigenen Pull Request.

besteht darauf, dass `lib/contentfly/composer.json` **keine** `version` deklariert — die

Den Lock mit `composer update areanet/contentfly --no-install` nachziehen. Wie bei `0084` prüfen,
dass sich nur `content-hash`, `version` und `reference` geändert haben: Composer 2.6 schreibt sonst
ungefragt Formatzeilen um (`{}` → `[]`, `plugin-api-version`), und die gehören nicht zum Bump.

### Abnahme
`tools/ci/bezugsweg-pruefen.sh` lokal, in einem Temp-Verzeichnis ausserhalb des Repos:

```
Version  v2.2.1
Quelle   git@github.com:area-net-gmbh/contentfly-framework-dist.git
✓ getaggte Version aus einem entfernten Repository
✓ data / errors / meta — Version 2.2.1
```

Also der **Tag**, kein `dev-*`, und der laufende Server meldet `2.2.1` in `meta.version`.

### Zwei Fehlschläge davor — beide in der Umgebung, keiner am Paket
Erwähnenswert, weil beide Male dieselbe irreführende Meldung kam: *„Repository not found."*

1. **Composer nahm HTTPS statt SSH.** `github-protocols` steht lokal auf `["https","ssh"]`, also
   HTTPS zuerst; Composer schrieb die SSH-URL um und authentifizierte sich mit dem Token aus
   `~/.composer/auth.json`, das auf das private Paket-Repository keinen Zugriff hat. Behoben mit
   einem isolierten `COMPOSER_HOME` für den Lauf — an der globalen Konfiguration wurde nichts
   geändert.
2. **Der falsche SSH-Schlüssel.** Der passende steht in der **lokalen** Repo-Konfiguration
   (`core.sshCommand` → `id_ed25519_areanet`), und die gilt nur innerhalb des Repos. Das Skript
   arbeitet bewusst ausserhalb, also greift sie dort nicht. Genau dafür setzt der CI-Job
   `GIT_SSH_COMMAND` ausdrücklich — der Skriptkopf nennt es als Voraussetzung, und es steht nur
   dort, weil git es aus der Umgebung liest und nicht aus dem Skript.

Daraus folgt ein Doku-Befund für einen eigenen Task: Wer das Paket **lokal** beziehen will, braucht
beides — `GIT_SSH_COMMAND` mit dem richtigen Schlüssel und ein Composer ohne konkurrierendes
GitHub-Token. Der Runbook beschreibt bisher nur die verwandte `dist`/`source`-Falle.
