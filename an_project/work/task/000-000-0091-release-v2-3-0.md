# Release v2.3.0 — die Rechte-Korrekturen seit v2.2.1 ausliefern

## Context
**Seit `v2.2.1` liegen vier Änderungen auf `master`, die ein Projekt spürt, aber nicht im Paket:**

| Task | PR | Was ein Projekt merkt |
|---|---|---|
| `000-000-0087` | #50 | Das Paket-Repository ist öffentlich: HTTPS statt SSH, kein Deploy Key, `preferred-install` entfällt |
| `000-000-0070` | #52 | Gruppenrechte bekommen keinen stillen Vollzugriff auf `PIM\Tag` mehr |
| `000-000-0088` | #55 | Mehrere Rechte-Zeilen je Entity: die restriktivste gilt; fehlerhafte `permissions` antworten 400 |
| `000-000-0090` | #56 | Rechte verwalten nur Admins — auch beim Schreiben; sonst 403 |

**`0090` ist eine Sicherheitskorrektur, und sie ist öffentlich einsehbar, seit ihr PR gemergt ist:**
Ein Nicht-Admin mit Schreibrecht auf `PIM\Group`, `PIM\Permission` oder `PIM\User` konnte sich zum
Admin machen. Ausgeliefert ist der Fix erst mit dem Tag — deshalb zeitnah.

**`v2.3.0`, nicht `v2.2.2`** — nach dem Massstab aus `0084` und `0086`: Ein Patch hat einen Eintrag
ohne Entfernung und ohne neuen Schlüssel, den kaum ein Projekt merkt. Hier sind es vier
Registereinträge mit geänderten Statuscodes und Rechten; `0070` und `0090` können einem Projekt
Rechte nehmen, die es bisher hatte.

### Abnahme
`tools/ci/bezugsweg-pruefen.sh` lokal, in einem Temp-Verzeichnis ausserhalb des Repos, ohne
Schlüssel und ohne Sondervariable für den Zugang:
```
Version  v2.3.0
Quelle   https://github.com/area-net-gmbh/contentfly-framework-dist.git
✓ getaggte Version aus einem entfernten Repository
✓ data / errors / meta — Version 2.3.0
```
Der erste Lauf scheiterte an der lokalen Umgebung, nicht am Paket: Das Skript erwartet die
Datenbank `bezugsweg_probe` fertig angelegt — in der Pipeline stellt der Service sie bereit, lokal
nicht. Angelegt, zweiter Lauf grün.

### Tagger und Autor falsch — `sim <sim@local>`
**Der Tag und sieben Commits tragen eine falsche Kennung.** Eine Merge-Simulation in einem
Wegwerf-Worktree setzte `user.name`/`user.email` per `git config` — in einem Worktree schreibt das
in die gemeinsame Konfiguration des Repos. Betroffen: der Tagger von `v2.3.0` und die Commits
`675cd653`, `70c74c84`, `b165a058`, `b19cf675`, `07cc80b6`, `02bb0895`, `b53aa084`, alle auf
`master`. Am Inhalt ändert das nichts. Die Konfiguration ist bereinigt; die Zuordnung zur richtigen
Kennung folgt über `.mailmap` in einem eigenen Task. Den Tag neu zu setzen hiesse, einen
veröffentlichten Tag zu löschen und die Veröffentlichung ein zweites Mal auszulösen — deshalb nicht.
