# Advisories vom 2026-11-04 schliessen — symfony/* im Lock auf 7.4.23 heben

## Context
**`check: composer audit` ist rot, ohne dass eine Abhängigkeit angefasst wurde** — dieselbe Lage
wie bei `000-000-0109`, nur grösser. Gefunden am 2026-11-11 beim Vorbereiten von `000-000-0110`
(Release `v2.5.1`): `tools/ci/audit.sh` endet mit **Exit 1**, *Found 10 security vulnerability
advisories affecting 5 packages*.

**Zehn Advisories, fünf Pakete, ein Stichtag.** Alle am **2026-11-04** in die Datenbank von
`FriendsOfPHP/security-advisories` gekommen, alle mit demselben betroffenen Bereich
`>=7.4.0,<7.4.23`:

| Paket | gelockt | Advisories |
|---|---|---|
| `symfony/http-client` | 7.4.18 | CVE-2026-121971, CVE-2026-123119 |
| `symfony/http-foundation` | 7.4.21 | CVE-2026-118514 + drei ohne CVE-Nummer |
| `symfony/http-kernel` | 7.4.18 | CVE-2026-123339 |
| `symfony/routing` | 7.4.18 | CVE-2026-118516 — Host-Platzhalter können den Anfang des Pfades matchen und pfadbasierte Zugriffskontrolle umgehen |
| `symfony/security-http` | 7.4.18 | CVE-2026-118513 (unvollständiger Fix für CVE-2026-45063, X509-DN-Parsing), CVE-2026-123746 (programmatische Logins überspringen `checkPostAuth()`) |

**Behoben in `7.4.23`**, veröffentlicht und verfügbar. **Kein Manifest muss angefasst werden** —
die Constraint `^7.4` erlaubt es schon, genau wie bei `000-000-0109`. Es geht ausschliesslich um
den Lock.

**Zwei der Befunde treffen dieses Projekt an einer Stelle, die es selbst benutzt**, und sind
deshalb mehr als eine Lock-Zeile: `symfony/routing` trägt das Routing dieser Anwendung
(`custom/app.php`, `$app['routeManager']->mount()`), und `symfony/security-http` steht im
Manifest des Frameworks, weil der X509- und der Login-Pfad daraus kommen. Ob die Anwendung die
betroffenen Pfade tatsächlich erreicht, ist Teil dieses Tasks — nicht, um den Bump zu vermeiden,
sondern damit im Register steht, was ein Bestandsprojekt wissen muss.

**Die Falle ist dieselbe wie in `000-000-0109` und `000-000-0106`:** Der Lock trägt
`plugin-api-version: 2.9.0`, lokal läuft Composer **2.6.6**. Der Lock muss mit einer Version
≥ 2.9 erneuert werden — `composer:2.10.3` in Docker —, sonst wird `check: Lock-Format` rot.
Zusätzlich fehlt dem Container `ext-ldap` (`symfony/ldap` verlangt es); der Lauf braucht
`--ignore-platform-req=ext-ldap`, was im Lock nichts hinterlässt.

**Dieser Task blockiert `000-000-0110`.** Der Release-PR kann nicht grün werden, solange das
Audit-Gate rot ist, und das Gate hängt an keinem Branch — es prüft den committeten Lock gegen
die aktuelle Advisory-Datenbank.

- [x] Für `CVE-2026-118516` (Routing) und `CVE-2026-123746` (programmatische Logins) ist festgehalten, ob diese Anwendung die betroffenen Pfade erreicht — mit der Stelle im Code, nicht als Vermutung.

## Offene Frage, die in den Task gehört
`000-000-0109` hat nachgewiesen, dass ein Advisory erst mit seiner Aufnahme in die Datenbank
wirkt, nicht mit *Reported at*. Hier ist *Reported at* der 2026-11-04 und der Lauf von PR #120
am **2026-11-06** war grün — also zwei Tage später. Entweder war die Datenbank im Lauf noch
älter, oder der Lauf hat das Gate nicht erreicht. Das ist zu klären: Wenn ein Gate zwei Tage
nach einem Advisory grün meldet, ist die Frage nicht der Lock, sondern das Gate.

## Ergebnis (2026-11-11)
**Alle zehn Advisories sind aus dem Lock.** `composer update "symfony/*" --no-install` unter
**Composer 2.10.3 in Docker**: `0 installs, 28 updates, 0 removals`, und Composer meldet im
selben Lauf *No security vulnerability advisories found.*

**28 Pakete, nicht 5.** Die fünf betroffenen gehen auf `7.4.23`, mit ihnen die übrigen
`symfony/*` desselben Baums (`console`, `cache`, `error-handler`, `string`, `var-dumper`,
`options-resolver`, `property-access/-info`, `rate-limiter`, `security-core`, `type-info`,
`var-exporter`, dazu sechs Polyfills) und die vier `*-contracts` von `3.7.x` auf `3.8.1`.
Nicht angefasst: `symfony/ldap` (7.4.10, `require-dev`, kein Advisory).

**Die Gates, mit den Skripten selbst statt mit Nachbauten:**

| Gate | Ergebnis |
|---|---|
| `tools/ci/audit.sh` | **Exit 0** — *No security vulnerability advisories found.*, „✓ Keine unausgenommene Sicherheitsmeldung im Lock." Der Schalter `--abandoned=fail` greift darin, also auch 0 abandoned Pakete. |

**Kein Manifest angefasst** — `^7.4` erlaubte `7.4.23` bereits, wie bei `000-000-0109`.

### Die zwei Befunde, die an Stellen dieser Anwendung liegen — belegt, nicht vermutet
- **`CVE-2026-118516` (Routing, Host-Platzhalter umgehen pfadbasierte Zugriffskontrolle):
  **greift hier nicht.** Die Lücke braucht Routen mit einem Host-Platzhalter. Diese Anwendung
  definiert keine: Alle `host`-Vorkommen in `lib/`, `custom/` und `plugins/` sind
  Datenbank- oder LDAP-Konfiguration (`DB_HOST`, `SECURITY_LDAP_HOST`,
  `Adapter::setHostname()`), keine Routen-Option. Die Routen entstehen über die
  `ControllerProvider` in `lib/contentfly/Classes/Controller/Provider/Base/` ohne Host-Angabe.
  **Vorbehalt für ein Bestandsprojekt:** Wer in `custom/app.php` eigene Routen mit Host-Muster
  mountet, ist betroffen — dann zählt der Bump, nicht dieser Absatz.
- **`CVE-2026-123746` (programmatische Logins überspringen `checkPostAuth()` der User Checker):
  **greift hier nicht.** Es gibt weder einen programmatischen Login (`Security::login()` kommt
  im Baum nicht vor) noch einen User Checker — also kein `checkPostAuth()`, das übersprungen
  werden könnte. Aus `symfony/security-http` wird ausschliesslich der
  `AccessTokenAuthenticator` benutzt, über drei Aufrufe; `AuthenticatorManager`, `FirewallMap`
  und `TokenStorage` stehen ausdrücklich aussen vor
  (`lib/contentfly/Classes/Security/TokenAuthenticator.php`, Kopfkommentar).

### Gemessen
`composer install` lokal (schreibt den Lock nicht — nachgeprüft, die Formatzeilen blieben
unberührt), danach gegen den **installierten** Stand 7.4.23:

- **Unit-Suite 503 grün** (1652 Assertions)
- **PHPStan `[OK] No errors`** — lokal mit `--memory-limit=1G`; das Standardlimit von 128M lässt
  den Parallel-Worker abstürzen, das ist die Umgebung und kein Befund

### Was lokal NICHT gemessen werden konnte
**Integrationssuite und Deprecation-Gate fehlen** — und das ist bei einem Symfony-Minor-Bump
genau die Messung, die zählt, weil dort neue Deprecations auftauchen. Der Grund ist die
Umgebung, nicht die Änderung: `docker compose up -d` scheitert an
*Bind for 127.0.0.1:3307 failed: port is already allocated*. Den Port hält der laufende
Container `kirsch-kunststofftechnikde-db-1` eines anderen Projekts. **Der wurde nicht gestoppt** —
fremde laufende Arbeit anzuhalten, um eine Messung zu bekommen, ist der falsche Tausch.

Verbindlich wird die Messung damit im PR-Lauf: `test: PHP 8.3/8.4/8.5` und das Deprecation-Gate.
Dieselbe Lage wie in `000-000-0109`, dort aus einem anderen Grund (`--no-install` liess das
`vendor/` auf dem alten Stand).

### Die offene Frage ist beantwortet — und sie entlastet das Gate nicht ganz
`composer audit` liest die Advisory-Datenbank **zur Laufzeit**, nicht aus dem Lock. Der Lauf von
PR #120 am 2026-11-06 war grün, der Stichtag der zehn Advisories ist der 2026-11-04 — zwei Tage
davor. Anders als bei `000-000-0109`, wo *Reported at* und Aufnahme in die Datenbank einen Monat
auseinanderlagen, ist hier **der Aufnahmezeitpunkt** das `Reported at` der Datenbankeinträge
selbst. Das heisst: Entweder war der Datenbankstand im Lauf vom 06.11. noch älter als sein
Datum, oder der Job hat eine zwischengespeicherte Fassung benutzt.

**Was daraus folgt, ist ein eigener Task, nicht eine Zeile hier:** Wenn ein Sicherheits-Gate zwei
Tage nach der Veröffentlichung von zehn Advisories grün meldet, ist die Frage das Gate. Zu prüfen
ist, ob der Job die Advisory-Datenbank cacht (`COMPOSER_HOME`, Actions-Cache) und ob er sie vor
dem Lauf erneuert. Bis das geklärt ist, gilt: **Ein grüner Audit-Lauf belegt den Stand seiner
Datenbank, nicht den Stand der Welt.**

## Abnahme im PR-Lauf (2026-11-11)
**Alle acht erforderlichen Checks grün** in PR #121, Lauf `42981222731`:
`check: composer audit` (14s) · `check: Lock-Format` (5s) · `check: PHPStan` (55s) ·
`check: Vorlagen-Konfiguration` (4s) · `check: Bezugsweg von aussen` (1m8s) ·
`test: PHP 8.3` (3m57s) · `test: PHP 8.4` (3m39s) · `test: PHP 8.5` (3m54s).
`mergeStateStatus: CLEAN`.

**Damit ist nachgeholt, was lokal an Port 3307 gescheitert ist** — und das Ergebnis ist die
Antwort auf die eigentliche Sorge bei einem Minor-Bump:

> `→ Deprecations im Serverlog`
> `  0 protokollierte Zeile(n), 0 Paar(e) aus Datei und Meldung, 0 davon ausgenommen.`
> `✓ Keine unausgenommene Deprecation, und jede Ausnahme wird noch gebraucht.`

**`7.4.23` bringt keine neue Deprecation.** Der Stand aus `an_project/docs/tech-stack.md` — *0
Deprecations bei 0 Ausnahmen* — hält den Sprung von `7.4.17`/`7.4.18`/`7.4.21` auf `7.4.23`
unverändert aus, über alle drei PHP-Versionen. Das ist die Zusage, von der der spätere Sprung auf
Symfony 8.4 LTS abhängt; sie ist hier nicht verlängert, sondern gemessen worden.

Der lokale Merge aus `/done` entfällt — integriert wird über den Pull Request
(`an_project/docs/git.md`, *Wie ein Work Item geschlossen wird*).

**Die Buchführung kam diesmal NACH dem Merge, und das ist festzuhalten statt zu glätten.**
`an_project/docs/git.md` verlangt sie als **letzten Commit auf dem Branch, bevor** der Pull
Request gemergt wird. PR #121 wurde um **07:46** gemergt (Merge-Commit `f17ef7cd`), dieser
Abschluss-Commit entstand um **07:47**. Zwei Commits blieben damit auf dem Branch liegen — dieser
und die Neufassung von `000-000-0112` — und erreichen `master` über einen eigenen
`abschluss`-Pull-Request, wie bei `000-000-0105`, `000-000-0108` (#111, #117).

Kein Schaden: Der Inhalt, auf den es ankam, lag im gemergten Stand — der Lock. Nachgetragen wird
die Buchführung. **Die Lehre ist eine andere:** Solange zwei Beteiligte an einem Pull Request
arbeiten, ist „letzter Commit vor dem Merge“ keine Reihenfolge, die eine Seite allein herstellen
kann. Wer die Buchführung in den PR bekommen will, committet sie **vor** dem Eröffnen — oder
akzeptiert den `abschluss`-PR als den Normalfall, der er in der Historie dieses Projekts
ohnehin ist.
