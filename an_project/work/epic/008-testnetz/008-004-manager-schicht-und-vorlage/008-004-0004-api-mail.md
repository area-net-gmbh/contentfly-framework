# /api/mail festhalten

## Context
Der einzige Endpunkt der API mit **Aussenwirkung**: Er verschickt eine Mail. Alles andere
schreibt höchstens in die Datenbank.

```php
$mailto = $request->get("mailto");
if(!$mailto){
    return new JsonResponse(array('message' => "No mailto address"), 500);
}
$data    = $request->get("data", array());
$subject = $request->get("subject", "Anfrage über PIM-API");

$body = "";
foreach($data as $name=>$value){
    $body .= $name.":\t\t\t".$value."\n";
}

mail($mailto, $subject, $body, 'From: '.APP_MAILFROM);
```

## Umfang

### Was festzuhalten ist
- **Der fehlende `mailto`** liefert HTTP 500 mit `{"message": "No mailto address"}` — einer
  der wenigen Fälle, in denen das Framework eine eigene Fehlermeldung formuliert statt eine
  Ausnahme durchzureichen. Festhalten.
- Die Form der Erfolgsantwort.
- Der Aufbau des Rumpfs aus `data`: `name` + Tabulatoren + `value`, je Zeile.
- Die Absicherung: ohne Token abgewiesen.

### Der springende Punkt: kein echter Versand
`mail()` ist eine PHP-Funktion, kein Dienst im Container — es gibt keinen Punkt, an dem sich
eine Attrappe einhängen ließe, ohne den Code zu ändern.

Mögliche Wege, beim Umsetzen zu entscheiden und zu begründen:
1. **`sendmail_path` im Testserver** auf ein Skript oder `/bin/true` setzen, sodass nichts
   das System verlässt. Der Testserver wird ohnehin eigens gestartet.
2. **Nur die Fehlerfälle testen**, in denen `mail()` gar nicht erreicht wird (fehlender
   `mailto`, fehlender Token) — ehrlich, aber deckt den Erfolgsfall nicht ab.
3. `mail()` gibt bei fehlgeschlagener Zustellung `false` zurück; ohne konfigurierten MTA
   scheitert der Aufruf ohnehin. Ob der Endpunkt das an den Client meldet, ist selbst eine
   Zusicherung, die festgehalten gehört.

**Auf keinen Fall** darf ein Testlauf eine Mail an eine echte Adresse schicken. Wenn kein
sicherer Weg für den Erfolgsfall gefunden wird, bleibt es bei Variante 2 — mit Begründung im
Testkommentar.

## Acceptance criteria
- [x] Der fehlende `mailto` ist mit Statuscode und Nutzlast festgehalten.
- [x] Die Absicherung ohne Token ist festgehalten.
- [x] Für den Erfolgsfall ist entweder ein sicherer Weg gefunden und dokumentiert, oder es ist
      begründet festgehalten, warum er nicht geprüft wird.
- [x] **Kein Testlauf verschickt eine Mail nach draussen** — das ist nachweislich
      sichergestellt, nicht angenommen.

## Verification
Mehrere vollständige Läufe. Der Nachweis, dass nichts hinausgeht, gehört ausdrücklich in die
Verifikation — etwa über die Konfiguration des Testservers.

## Ergebnis
`tests/Integration/Api/MailApiTest.php` — 14 Tests, 31 Assertions. Gesamtsuite
220 Tests / 511 Assertions (vorher 206 / 480). Drei Gesamtläufe, Postausgang danach leer.

### Der Befund, der den Task bestimmt hat
**`/api/mail` kann keine Mail verschicken.** `mailAction()` liest die Absenderadresse als
*nackte Konstante*:

```php
mail($mailto, $subject, $body, 'From: '.APP_MAILFROM);
```

`APP_MAILFROM` ist nirgends per `define()` gesetzt — es gibt nur ein gleichnamiges
**Konfigurationsfeld** in `Classes/Config.php`, erreichbar über `Adapter::getConfig()`. Unter
PHP 8 ist eine undefinierte Konstante ein `Error`:

```
Error: Undefined constant "Areanet\PIM\Controller\APP_MAILFROM"
```

Unter PHP 7 wäre derselbe Ausdruck noch als Zeichenkette `"APP_MAILFROM"` durchgegangen und
hätte einen unsinnigen, aber funktionierenden `From`-Kopf ergeben. Der Endpunkt hat also
einmal funktioniert und ist mit dem Sprung auf PHP 8 gestorben, ohne dass es auffiel.

Damit beantwortet sich die Frage des Umfangs von selbst: Es gibt keinen Erfolgsfall, der
sicher zu prüfen wäre — es gibt gar keinen.

### Die Sicherung gegen echten Versand
Sie hängt bewusst **nicht** an diesem Fehler, sonst würde seine Reparatur den Schutz
mitentfernen. Der Testserver bekommt ein Fangskript als `sendmail_path`;
`testDieVersandfalleIstScharf()` belegt beide Hälften:

- **Fängt das Skript?** Der Test löst es einmal absichtlich in einem eigenen PHP-Prozess aus
  und schneidet den Eintrag danach wieder heraus.
- **Benutzt der Server es?** Über `/__test/sendmail-path`, einen Diagnosepfad in
  `tests/router.php` — Testinfrastruktur, in keiner Installation vorhanden.

Beide Gegenproben wurden durchgespielt: Ohne `CONTENTFLY_TEST_MAIL_TRAP` werden die drei
betroffenen Tests **übersprungen**, nicht durchgewinkt; gegen einen Server ohne die Umleitung
**scheitert** der Test und nennt den echten MTA (`/usr/sbin/sendmail -t -i`). Einrichtung in
`tests/README.md`.

### Weiter festgehalten
- Ohne Token: `500` statt `401`, wie bei jeder gesicherten `/api`-Route (`000-000-0006`).
- Fehlender `mailto`: `500` mit exakt `{"message":"No mailto address"}` — einer der wenigen
  Fälle mit eigener Fehlermeldung statt durchgereichter Ausnahme.
- Die Prüfung ist `if(!$mailto)`: jeder falsy Wert gilt als fehlend, auch die Zeichenkette
  `"0"`.
- Nur `POST`; `GET` ergibt `405`.
- Am Quelltext festgehalten, weil nicht erreichbar: der Rumpfaufbau
  `name` + drei Tabulatoren + `value`, und die **doppelt kodierte** Erfolgsantwort
  (`json_encode` in eine Zeichenkette, die dann in `data` liegt) — gehört zu `000-000-0014`.

### Befunde → `000-000-0016`
1. Der undefinierte `APP_MAILFROM` — der Endpunkt ist funktionslos.
2. **Warnung im Ticket:** Wer nur die Konstante repariert, schaltet ein Mail-Relais hinter
   einem Token frei. Empfänger, Betreff und Inhalt kommen ungeprüft vom Aufrufer, es gibt
   keine Validierung, keine Begrenzung und keine Rechteprüfung über das Token hinaus.
3. Die doppelt kodierte Erfolgsantwort.
